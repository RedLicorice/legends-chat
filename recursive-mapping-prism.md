# Legends Chat — Initial Architecture & Build Plan

## Context

Greenfield repo. Goal: a PWA chat app for a single community (one workspace, many "topic" rooms — Telegram-forum style). Auth is delegated to a Telegram bot via one-time invite/login codes. Roles: User / Moderator / Admin. Bots are first-class with a Telegram-inspired API. Hosting is containerized and horizontally scalable.

**E2EE is out of scope for now** but the architecture leaves room for it: messages are stored as ciphertext+nonce regardless, so a future E2EE layer just slots in client-side before the existing encryption-at-rest layer without a schema migration.

This plan covers the foundational scaffold and the first vertical slice (auth → topic list → topic view → send/receive messages). Bots, E2EE, reactions, and inline keyboards are scaffolded as schema + interfaces but only minimally implemented in slice 1.

## Decisions locked in (from clarification round)

- **Stack**: Next.js 15 (App Router) PWA, TypeScript, Tailwind + shadcn/ui + Framer Motion + Lucide, Postgres + Drizzle ORM, Socket.IO over HTTPS, Redis (pub/sub for WS fanout + ephemeral state), Web Push (VAPID) for notifications.
- **Telegram bot**: separate Node process using **grammY**, sharing types and Drizzle schema via a workspace package.
- **Hosting**: Docker Compose for dev; production = horizontally scalable containers (web + ws + bot + postgres + redis).
- **E2EE**: deferred. Not built in any slice below. The data model carries an `isE2ee` boolean and stores ciphertext+nonce so a future E2EE layer can be added without migrations or breaking changes. For now every topic is treated as non-E2EE.
- **Onboarding**: Telegram bot is public. New user DMs `/start` → bot asks for invite code → code validated → account created (role=User) → bot returns deep link to app for login. Existing user `/start` → bot recognizes them → returns fresh login deep link. Invite codes are generated by members with the `invites.create` permission; daily quota per role is configurable in admin settings.
- **Topics**: forum-style rooms inside a single community workspace. Sticky flag, unread count tracked server-side via `last_read_message_id` per (user, topic). For E2EE topics, server cannot show a "last message preview" — client caches it locally; server just shows sender + timestamp.
- **History config**: per-topic admin settings:
  - `historyVisibleToNewMembers: bool`
  - `autoDeleteMode`: `none` | `age` | `count`
    - `age` → set `autoDeleteAgeSeconds` (e.g. delete messages older than 1 day)
    - `count` → set `autoDeleteMaxMessages` (e.g. keep only the most recent 1000)
  - The two modes are mutually exclusive per topic. Admin UI uses a segmented control.

## Data model (Drizzle, Postgres) — first cut

- `users` — id, telegramUserId (unique), telegramUsername, displayName, avatarUrl, role, createdAt, lastSeenAt
- `roles_permissions` — seeded table mapping role → permission keys (so admins can tune later without code changes)
- `invite_codes` — code, createdByUserId, usedByUserId nullable, expiresAt, createdAt
- `invite_quota_config` — role, dailyLimit (admin-editable)
- `auth_login_tokens` — token, userId, expiresAt, consumedAt (one-time, short-lived, issued by bot)
- `sessions` — id, userId, refreshTokenHash, deviceLabel, createdAt, revokedAt
- `topics` — id, slug, title, description, isSticky, sortOrder, isE2ee, historyVisibleToNewMembers, **autoDeleteMode** (`none` | `age` | `count`), **autoDeleteAgeSeconds** nullable, **autoDeleteMaxMessages** nullable, createdAt. `messageTtlDays` is folded into `autoDeleteMode='age'`.
- `topic_members` — topicId, userId, joinedAt, lastReadMessageId, mutedUntil
- `messages` — id, topicId, senderUserId nullable (null = bot), botId nullable, replyToMessageId nullable, **contentCiphertext (bytea, always)**, contentNonce (bytea), keyId (FK → `encryption_keys`), createdAt, editedAt, deletedAt. Even non-E2EE topics store ciphertext — see "Server-side encryption at rest" below.
- `encryption_keys` — id, purpose (`messages` | `attachments`), algorithm (`xchacha20poly1305`), wrappedKey (bytea, wrapped by the master key from KMS/env), createdAt, rotatedAt nullable. Allows key rotation without re-encrypting history.
- `message_reactions` — messageId, userId, emojiKey (FK to emoji pack), createdAt
- `bots` — id, name, ownerUserId, tokenHash, avatarUrl, isActive, createdAt
- `bot_keyboards` — denormalized inline keyboard payloads referenced by messages (jsonb)
- `push_subscriptions` — userId, endpoint, p256dh, auth, deviceLabel
- `audit_log` — actorUserId, action, targetType, targetId, metadata, createdAt
- `message_flags` — id, messageId, reporterUserId, reason (free text, required), status (`pending` | `dismissed` | `actioned`), reviewedByUserId nullable, reviewedAt nullable, createdAt
- `user_bans` — id, userId, bannedByUserId, reason (required), sourceFlagId nullable, createdAt, **expiresAt nullable** (null = permanent), liftedByUserId nullable, liftedAt nullable. A user is currently banned iff they have a row with `liftedAt IS NULL` AND (`expiresAt IS NULL` OR `expiresAt > now()`).
- `user_mutes` — same shape as `user_bans` (userId, mutedByUserId, reason required, sourceFlagId nullable, createdAt, expiresAt nullable, liftedByUserId nullable, liftedAt nullable). A muted user can still log in and read everything, but cannot send messages, reactions, or flags.
- `registration_config` — singleton row: `invitesEnabled bool`, `publicRegistrationEnabled bool`, plus the existing per-role invite quota config. Editable from the admin UI.

Permissions are string keys checked via a single `can(user, key, ctx?)` helper in `packages/shared`. Initial keys include:

- `topics.create`, `messages.delete.any`, `invites.create`, `bots.manage`
- `messages.flag` — flag content into the moderator queue (granted broadly, e.g. all Users by default; revocable per-user as an anti-abuse measure)
- `moderation.queue.review` — view and act on the flag queue (Moderator+)
- `users.ban.direct` — ban a user without going through the queue (Moderator+ / Admin per config)
- `users.ban.lift` — lift an existing ban (Admin by default)

## Auth flow

1. User DMs Telegram bot (`apps/bot`).
2. `/start` → bot looks up `telegramUserId` in `users`.
   - **If banned** (active row in `user_bans`): bot replies with the reason and, if `expiresAt` is set, the **time remaining** ("Banned for: <reason>. Time remaining: 2d 4h 17m"). If permanent, says "This ban is permanent." No login link issued.
   - **If unknown**: bot reads `registration_config`:
     - If `invitesEnabled` → ask for invite code; on valid code → create user, consume code, log audit event.
     - Else if `publicRegistrationEnabled` → create the user immediately as role=User, log audit event.
     - Else → reply "Sorry, we're not accepting new members at the moment." and stop.
   - **If known and not banned**: continue (mute does not block login).
3. Bot generates a row in `auth_login_tokens` (32-byte random, 5-min TTL, single-use) and replies with `https://app.example.com/auth/callback?token=...`.
4. Web app `/auth/callback` consumes the token and issues **JWTs**:
   - **Access JWT** (~15 min, signed with HS256 or EdDSA): payload `{sub, role, jti, iat, exp}`. Stored in an httpOnly Secure SameSite=Lax cookie.
   - **Refresh JWT** (~30 days, separate signing key): also httpOnly. `jti` is recorded in the `sessions` table so it can be revoked individually.
5. Socket.IO connection authenticates by reading the access JWT cookie in middleware and verifying signature + expiry locally (no DB hit on the hot path). Revocation handled via a small Redis set of revoked `jti`s checked on connect and on a short interval.

**Why JWT not opaque sessions:** lets the WS layer verify auth without a DB round-trip, which matters when scaling out the WS pods. Revocation is still possible because each token carries a `jti` we can blocklist (used for ban, mute escalation, manual session kill).

### Ban enforcement

- Banning a user (from queue or direct) does three things atomically:
  1. Inserts a `user_bans` row (with required reason and optional expiresAt).
  2. Adds every active session `jti` for that user to the Redis revocation set (TTL = remaining access-token lifetime, so the set stays small).
  3. Publishes a `user:banned` event on Redis. The WS layer subscribes and force-disconnects every live socket for that user.
- Every authenticated HTTP request and WS message runs a fast `isBanned(userId)` check (Redis-cached, invalidated on ban/unban).
- Bot's `/start` path also checks `isBanned` before issuing a login token, so a banned user cannot re-enter even with a fresh Telegram session.

### Mute enforcement

- Mute is a separate moderation action with the same UX shape as ban (required reason, duration chips, can be permanent).
- A muted user keeps their session and can read everything in real time. The server **rejects** any write attempt — `message:send`, `reaction:add`, `messages.flag`, bot API calls made on their behalf — with a `MUTED` error containing the reason and `expiresAt`.
- The web client surfaces the mute state in the composer (disabled input + banner: "You are muted: <reason>. <time remaining>").
- Permission keys: `users.mute.direct`, `users.mute.lift`. Moderation queue gains a third action **Action: mute user** alongside dismiss/delete/ban.

## Moderation queue

- Any user with `messages.flag` can flag a message. UI: long-press / context menu → "Report" → reason required.
- Flags create a `message_flags` row with `status='pending'` and surface in `/admin/moderation` for users with `moderation.queue.review`.
- Reviewer actions:
  - **Dismiss** — sets `status='dismissed'`, requires no extra input.
  - **Action: delete message only** — soft-deletes the message, sets `status='actioned'`.
  - **Action: ban user** — opens a modal requiring a ban reason (free text, min length enforced) and a **duration** (preset chips: 1h / 24h / 7d / 30d / Permanent, plus a custom field). Creates `user_bans` row with `expiresAt = now + duration` (or null for permanent), linked to `sourceFlagId`, soft-deletes the message, sets `status='actioned'`.
- Direct ban (no flag): users with `users.ban.direct` can ban from a user's profile page. Same required-reason + duration modal. `sourceFlagId` is null in this case.
- A lightweight cron (or just lazy check on each `isBanned` call) is enough — no scheduled job strictly required since the check is `expiresAt > now()`.
- All ban/unban/flag-resolution actions write to `audit_log`.

## Realtime layer

- `apps/ws` is a standalone Socket.IO server. Clients connect to `wss://app.example.com/ws`.
- Rooms: one Socket.IO room per topic (`topic:<id>`) and one per user (`user:<id>` for presence/notifications).
- Horizontal scaling via `@socket.io/redis-adapter`.
- Events (names in `packages/shared/events.ts`):
  - `message:new`, `message:edit`, `message:delete`
  - `reaction:add`, `reaction:remove`
  - `topic:read` (client → server, updates `lastReadMessageId`)
  - `presence:update`, `typing:start`, `typing:stop`
  - `bot:keyboard:callback` (button taps from inline keyboards)

## Bot API (Telegram-inspired, internal to this app — separate from the Telegram-login bot)

In `apps/web/app/api/bot/v1/...`. Bots authenticate with `Authorization: Bearer <bot-token>`. Initial endpoints:

- `POST /sendMessage` — `{topicId, text, replyToMessageId?, inlineKeyboard?}`
- `POST /editMessage`, `POST /deleteMessage`
- `POST /answerCallbackQuery` — for button taps
- `GET /getUpdates` long-poll OR webhook config (start with webhook only — simpler at scale)
- `POST /setWebhook` — bot owner sets a URL the server POSTs to on relevant events

Events delivered to bot webhooks: `message`, `callback_query`, `member_joined`, `member_left`. Payload shapes intentionally mirror Telegram's Update object so existing Telegram bot devs feel at home.

Bots are scoped to topics via `topic_bots` join table (added in slice 2). Adding a bot to an E2EE topic is rejected by the API (E2EE topics are bot-free by definition).

## Encryption

### Server-side encryption at rest (always on, in scope now)

- **Every** message body is stored encrypted in the database. Disk dumps, stolen backups, or a compromised DB read do not yield plaintext.
- Algorithm: XChaCha20-Poly1305 (libsodium / `@noble/ciphers`). Per-message random nonce, AAD = `{messageId, topicId, createdAt}`.
- Master key supplied via env var or KMS (AWS KMS / GCP KMS / HashiCorp Vault — pluggable). Master key wraps the row keys in `encryption_keys`. Rotation = new row in `encryption_keys`, old rows still decryptable via their original `keyId`.
- The Node app process holds the unwrapped current key in memory only. All read paths transparently decrypt before serving.
- This gives bots, search, moderation, and unread-preview server-side functionality while still protecting data at rest.

### End-to-end encryption (deferred, architecturally reserved)

Not in scope for now, but the following decisions keep the door open so adding it later is additive rather than a rewrite:

- `topics.isE2ee` boolean is in the schema from day one (always `false` for now).
- Messages are already stored as `contentCiphertext` + `contentNonce`, so a future client-side ratchet layer just nests inside the existing at-rest ciphertext without a migration.
- The bot API is designed assuming bots can read messages — when E2EE arrives, the rule will be "bots cannot be added to E2EE topics," which is straightforward to enforce later.
- No client-side key storage / IndexedDB code is written yet.

## Auto-delete worker

A small worker (running inside `apps/ws` or as its own tiny process — decide at implementation time based on whether we want to scale it independently) handles per-topic retention:

- **Age mode**: every minute, for each topic with `autoDeleteMode='age'`, run `DELETE FROM messages WHERE topicId=$1 AND createdAt < now() - $2::interval`. Cheap with a `(topicId, createdAt)` index.
- **Count mode**: triggered after each insert (cheap because it only fires for topics in count mode) — `DELETE FROM messages WHERE topicId=$1 AND id NOT IN (SELECT id FROM messages WHERE topicId=$1 ORDER BY createdAt DESC LIMIT $2)`. Done as a Postgres trigger or in app code; trigger is simpler and keeps logic atomic with the insert.
- Deletes are hard deletes (purpose of the feature is actual data minimization), and emit `message:delete` over Socket.IO so connected clients drop them from view immediately.
- Audit log records "auto-delete: N messages from topic X" once per worker tick, not per message, to avoid spam.
